DuckDB at Scale

Can a self-hosted DuckDB stack carry the platform for the foreseeable future, including at enterprise scale? Yes, with one reframing: DuckDB is the execution engine, not the warehouse. The warehouse is the table format, the catalog and the serving layer you put around it. Get those three right and the answer holds well past where most teams actually are. Get them wrong and you have a fast library with no front door.

The reframing

"Self-hosting DuckDB" is a slight category error. DuckDB is an in-process library, like SQLite. There is no server to host, no daemon, no port. So the real question is: which architecture do you build around the library? There are four, and only two of them scale.

Truly distributed DuckDB, where one query fans out across machines, exists only at the edges: MotherDuck (a paid service, ruled out by principle 5) and DeepSeek's Smallpond (partition-parallel DuckDB over Ray and their 3FS filesystem, released 2025). Neither is needed if a single node can execute any one query and the catalog handles the rest, which is the bet the lakehouse architecture makes.

Where the single-node bet holds

The bet is that no individual query needs more than one large machine. Three pieces of evidence say that is true for most organisations most of the time.

  • Data volumes are smaller than the industry narrative. The MotherDuck founders' 2023 analysis of warehouse customer data argued that most organisations hold well under a terabyte of analytical data and most queries touch a small fraction of it. Cloud warehouses were built for the long tail of giants; the median customer is not one.
  • DuckDB executes out of core. Since the 1.x series, joins, aggregations and sorts spill to disk when they exceed memory_limit. Published runs of the TPC-H benchmark at the 100 GB scale factor complete on a laptop; the 1 TB scale factor completes on a single large cloud instance. The ceiling is NVMe throughput on the box, not RAM.
  • Vertical scale is cheap now. A single EKS node with 64 cores, 512 GB of RAM and local NVMe is an ordinary instance type. Two of them, stateless, behind Temporal, is more compute than a small team's marts will use.

DuckDB is also no longer a research project. Version 1.0 landed in June 2024; 1.4 in September 2025 was the first long-term-support release with a year of patches, database encryption at rest, MERGE INTO, and Iceberg writes. It is embedded in shipping products from Fivetran, Hugging Face and Rill among others. The engine is not the risk.

Where it genuinely falls short, and what closes each gap

These are the things Redshift gives you on day one that a library cannot. Each one has a self-hosted answer, but every answer is a component you now run.

Hard gap

No authentication, roles, row-level security or audit log

A library has no users. Anyone who can open the file or read the bucket can read everything. Enterprise means someone will ask for column masking and a query log by user within a year.

Closed by: the Postgres front end. pg_duckdb puts Postgres roles, GRANT, row-level security policies and pgaudit in front of DuckDB execution. Bucket access uses IAM roles for service accounts on EKS, so workers never hold long-lived keys. This is the single most important reason the serving layer is Postgres and not a custom Go API.

Hard gap

Multi-writer to one table

Two Temporal workers cannot both write into one .duckdb file. Your spec sidesteps this for bronze by giving each worker its own partition files, but marts built by dbt are a single target.

Closed by: the table format. DuckLake stores table metadata in Postgres and data as Parquet; concurrent DuckDB clients commit through Postgres transactions, giving ACID multi-table writes, snapshots and time travel. Iceberg does the same through a REST catalog. Either way, "the warehouse" becomes a catalog database plus a bucket, and any number of dbt-duckdb processes can build different marts concurrently.

Soft gap

Concurrent interactive users

Each DuckDB process is independent. Fifty analysts each firing dashboard queries is fifty engines each with its own memory budget, and nothing arbitrates between them. Redshift has workload management and concurrency scaling; DuckDB has neither.

Closed by: the serving layer plus discipline. Postgres connection pooling (PgBouncer) caps concurrency; per-role memory_limit and threads settings bound each session; marts are pre-aggregated so dashboard queries are small. This is the dimension to load-test before committing, because it is the one that fails gradually rather than loudly.

Soft gap

High availability

There is no DuckDB failover because there is no DuckDB server. Put differently, HA is not the engine's problem.

Closed by: statelessness. Workers hold nothing durable; kill one and Temporal reschedules the activity. The only stateful component is the Postgres catalog, which gets Multi-AZ RDS or a Postgres operator with replicas. This is the same HA story as any lakehouse, and it is simpler than a Redshift cluster's.

Soft gap

BI tool ecosystem

Redshift is a first-class connector in every BI tool. DuckDB's Metabase driver is a community plugin; Grafana's DuckDB plugin comes from MotherDuck; Tableau and Power BI go through DuckDB's JDBC and ODBC drivers.

Closed by: Postgres wire. Every BI tool ever made speaks Postgres. Metabase, Grafana, Superset, Tableau and Power BI connect to pg_duckdb as a Postgres database and never know DuckDB is underneath. This also answers your visualiser question directly: concurrent reads go through Postgres, and never touch a file a writer holds.

Organisational

Support, hiring and the "who do we call" question

Redshift comes with an AWS support contract and a large hiring pool. DuckDB Labs offers paid support; MotherDuck is the commercial path and is a subscription. A team inheriting this stack needs to understand a catalog, a table format and a Postgres extension, not one product.

Mitigated by: the ground truth being Parquet on S3. Whatever happens to DuckLake or pg_duckdb, Redshift Spectrum, Athena, Trino and Spark all read the data as it sits. The exit cost is a dbt profile change and a catalog re-registration, which is the lowest lock-in of any warehouse choice available to you.

How concurrency actually works here

  • Writers: each dbt-duckdb pod attaches DuckLake with its own DuckDB. Commits go through Postgres transactions, so two pods building different marts do not conflict, and two building the same mart serialise cleanly.
  • Readers: BI tools query Postgres. pg_duckdb reads the current DuckLake snapshot and the Parquet behind it. No reader ever opens a file a writer has open, because there is no shared .duckdb file anywhere in the design.
  • Go: reads marts over the Postgres wire with pgx, so the Go binary stays CGO-free, exactly as the spec's principle 6 wants.

What you run that Redshift would run for you

  • One Postgres (RDS is fine and approved). Backups, minor upgrades, a Multi-AZ toggle.
  • The pg_duckdb extension version, pinned, tested on upgrade. RDS does not ship it, so this is a Postgres pod with the extension, or a self-managed instance. That is the operational cost of the front door.
  • DuckDB and DuckLake extension versions in the dbt image, pinned together.
  • Node sizing for the dbt pods: memory and NVMe for spill.

Why DuckLake over Iceberg here. Both work. DuckLake is simpler to operate (the catalog is plain Postgres tables, no REST catalog service, no Glue), has faster small commits, and is native to DuckDB. Iceberg has the broader ecosystem and is what Redshift Spectrum reads. If you ever want Redshift alongside, or the org standardises on Iceberg, DuckDB 1.4 writes Iceberg too, so the marts can be re-materialised. Start with DuckLake for the learning project; the spec's Parquet-first bronze is engine-neutral either way.

Recommendation

Make the self-hosted DuckDB lakehouse the primary phase-2 path and Redshift the escape hatch, with the switch governed by named triggers rather than a feeling. The spec's "warehouse is the contract" principle means both can coexist: dbt gets two targets, bronze is shared, and moving marts is a re-materialisation, not a migration.

Triggers that would move marts to Redshift

  • Hot mart data exceeds roughly five terabytes and partition pruning no longer keeps the largest mart under an hour to rebuild.
  • More than about fifty concurrent BI sessions, with P95 dashboard latency over the target after PgBouncer and pre-aggregation.
  • A security or compliance requirement that Postgres roles, RLS and pgaudit cannot satisfy, or that requires a vendor's certification.
  • DuckLake or pg_duckdb ships a breaking change the team cannot absorb, or either project stalls for two consecutive quarters.

What to prove before phase 2 commits

  1. Two dbt-duckdb pods building different marts against one DuckLake catalog
    Proves multi-writer coordination. Then run the same mart from both and confirm the second commit serialises rather than corrupts.
  2. Load test the serving layer
    Twenty, then fifty simulated dashboard sessions through PgBouncer into pg_duckdb. Record P95 latency and node memory. This is the number that decides the envelope.
  3. Kill a dbt pod mid-build
    Confirm the DuckLake snapshot is intact and Temporal re-runs the activity cleanly. This is the HA story; make sure it is true.
  4. Point a Redshift Spectrum external schema at the same bronze bucket
    Proves the escape hatch is real. Run the staging models against both targets with dbt compile.
  5. Time-travel a mart
    Query a DuckLake snapshot from a week earlier. Cheap to test, and the feature that makes debugging a bad build pleasant.

One honest caveat about the "foreseeable future" framing. The engine will be fine. The pieces that make it a warehouse, DuckLake and pg_duckdb, are a year or two old. Pin versions, keep bronze as the only ground truth, and re-check both projects at each phase boundary. That discipline is what makes "DuckDB for the foreseeable future" a strategy rather than a bet.
