What the spec gets right

These are worth naming because they are the things people usually get wrong, and they are the reason the rest of this review is about seams rather than structure.

  • The warehouse is the contract. Making table names the only shared vocabulary between dbt and Go is exactly how you keep two transformation languages from becoming one tangle. It is also what makes the warehouse swappable later.
  • Immutable bronze with deterministic paths. Window-derived paths plus overwrite-on-rerun is the correct idempotency mechanism. It gives you backfill for free and makes every downstream layer disposable.
  • Ingestion never transforms. The single most common source of unreproducible pipelines is cleaning in the loader. Pushing that into staging views means a bad cast is a one-line SQL fix, not a re-extract.
  • Staging as views, marts as tables, incremental only when slow. The right default ordering. Most learning projects reach for incremental models on day one and spend weeks debugging merge keys.
  • Tests placed by layer, freshness on raw. Source freshness is the test that catches the failure mode nobody sees: the extractor quietly stopping. Good instinct to call it out.
  • Iceberg deferred. Correct for phase 1. See the warehouse section for why it may matter earlier than "Later".

Findings

Graded by what happens if you build without resolving them. Blockers change the shape of the code. Should-fix items cost a rewrite of one component or a confusing week. Consider items are opinions.

Blocker
Spec §3, §4, §5 · Diagram P→RAW, "raw tables loaded by Go"

How raw tables get into the warehouse is undecided, and the two answers imply different code

The spec says raw tables are "loaded by Go with no logic". In phase 1 that is not what happens: DuckDB reads Parquet in place, so there is no load step and Go never touches the warehouse. dbt-duckdb declares the Parquet path as an external source in sources.yml and the "raw table" is just a name over files. In phase 2 you face a real fork: COPY into Redshift (Go or dbt issues a load, data is duplicated, warehouse has its own copy) versus Redshift Spectrum external tables (zero-copy over S3, requires a Glue Data Catalog, raw stays Parquet-only).

Recommendation: commit to external tables in both phases. It honours principle 2 (Parquet is the only durable thing), principle 4 (storage separate from compute), and it means Go has no warehouse write path at all. Change the wording to "raw tables are external tables over bronze Parquet; nothing loads them." Note Glue Data Catalog as a phase-2 dependency. If you later want the COPY pattern for query speed, it becomes a dbt model that materialises raw into a native table, which keeps it inside the dbt lineage graph.

Blocker
Spec "Requirement: idempotent re-runs", §2 Runner

Extraction window granularity and schedule cadence are not the same thing, and the spec conflates them

"One file per source per time window" is only idempotent if the window is fully re-fetchable. A ticker running every 15 minutes writing daily-partitioned files has to choose: re-fetch the whole day each tick and overwrite (only works if the source serves history), or write a 15-minute file (96 files a day per source, which DuckDB tolerates and Spectrum/Athena punish). Sensor data also arrives late, so yesterday's file is not final at midnight.

Recommendation: define three parameters explicitly: window (the unit of a file, e.g. one hour), cadence (how often the runner fires), and lookback (how many trailing windows each run re-extracts to absorb late data). Add a compaction job later that rolls hourly files into one daily file once a day is closed. That is a classic Go job and a real data-engineering lesson. Also state which sources support history fetch; a source that only serves "current value" cannot be re-extracted and needs staging-level dedupe as the spec's fallback describes.

Should fix
Diagram W node · Spec idempotency

Diagram says the Writer "appends Parquet"; the spec forbids appending

Parquet cannot be appended to anyway. The format writes its schema and row-group index in a footer, so "append" means read, merge, rewrite. The spec is right and the diagram is wrong. Small, but it is the kind of drift that a future reader trusts the picture over the prose on.

Fix: "writes one Parquet file per window, overwrite on re-run". The corrected diagram below has it.

Should fix
Diagram GT→RAW · Spec §6

Go transforms are drawn writing into the raw layer, and have no input arrow

Go transform output is derived data, not raw. Putting it in RAW breaks the medallion promise that raw is what the source said. The diagram also shows Go transforms reading nothing, when in practice they consume staging or mart tables.

Recommendation: give Go transforms their own zone in bronze, e.g. derived/<transform>/<window>.parquet, written by the same Writer, and declare them in sources.yml as the spec already says. Then dbt marts can build on top of them and the lineage graph shows the hop honestly. This also means Go needs no DuckDB driver at all in phase 1: read Parquet with parquet-go or Arrow, write Parquet, done. That matters because go-duckdb requires CGO, which complicates cross-compiling the EKS image. Keep DuckDB out of the Go binary unless a transform genuinely needs SQL from Go.

Should fix
Spec §4 phase 1, §9

DuckDB allows one read-write process, or many read-only processes, never both. Metabase will collide with dbt build

A DuckDB file can be open by one process in read-write mode, or by several in read-only mode. Not a mix. Metabase holding a connection while dbt build runs will fail one side or the other. Metabase's DuckDB driver is also a community plugin from MotherDuck, not bundled, and lags Metabase releases.

Options: (a) have dbt write marts as Parquet using dbt-duckdb's external materialisation, and point a second, read-only DuckDB at those files for Metabase; (b) build into a temp database file and atomically rename it over the served one; (c) skip Metabase in phase 1 and use DuckDB's built-in UI (duckdb -ui) for validation, which is what the spec says Metabase is for anyway. Option (c) is the least work and delays the Metabase driver question to the Redshift phase where it is a first-class driver.

Should fix
Spec §1 Sources

The first source is not concrete

"Plant sensor readings" has no device, API, cadence, or history semantics attached. I checked Home Assistant on thechengvault.local and it has no plant, moisture, or soil entities. So the Fetcher has nothing to fetch yet, and the window question above cannot be answered without knowing whether the source serves history.

Recommendation: either name the device and its API before writing the Fetcher, or start with a source that already exists and has clean history semantics. The beads tracker is a strong candidate: Dolt speaks the MySQL wire protocol, go-sql-driver/mysql reads it, every row has timestamps, and issue-state history is genuinely interesting to model. Sensors can be source two.

Should fix
Spec Principle 5, §4 phase 2, §9

"Free and open source only" contradicts Redshift, Athena and QuickSight

Principle 5 as written excludes the whole phase-2 AWS stack. What the principle actually means is "no paid SaaS tiers for tooling; managed AWS compute is acceptable because the org already pays for it".

Fix: reword to "Open-source tooling; AWS managed services allowed where already approved in org. No new vendor subscriptions." That also matches the standing no-new-subscriptions rule in this workspace.

Consider
Spec §3, §7

Small gaps that cost little to close now

  • Metadata columns are not transformation. State that the Writer stamps _extracted_at, _window_start, _source_file on every row. Freshness tests need the first one.
  • Schema evolution in bronze. When a sensor grows a field, old files lack it. DuckDB handles this with read_parquet(..., union_by_name=true); say so, and keep staging models explicit about columns so a new field cannot silently reach marts.
  • Timezones. Bronze stores UTC. Staging converts to Australia/Sydney for daily aggregates. Daily averages that straddle a DST change are a good test case for the marts.
  • Backfill as a first-class command. The idempotency design makes ingest --from --to trivial. Name it in the Runner section so it gets built.
  • Pipeline observability. Row counts, durations, and run outcomes from the Go orchestrator, and dbt's run_results.json, are natural OTel emissions. This workspace already has the Grafana Cloud plumbing; reuse it rather than adding a data-observability tool.
  • Configuration and secrets. The spec is silent on how a Fetcher gets credentials. Env vars locally, Kubernetes secrets on EKS, one Config struct per fetcher.

Recommendation

Temporal, and earlier than the spec says. The spec defers it until "several pipelines with real dependency ordering", but a ticker-based Runner is throwaway once Temporal arrives, and the point of the project is to learn the tool. The dev server costs nothing to run locally.

Do it in two moves. First, write Fetcher and Writer as plain functions with context and error returns, and keep the Runner a thin loop. Second, once one source works end to end, wrap those same functions as Activities inside an IngestWindow Workflow, drive it with a Temporal Schedule, and delete the ticker. Nothing in Fetcher or Writer changes.

Why the others stay one adapter away

Because the Go binaries do all the work and the warehouse is the contract, Airflow can wrap the same binaries with a KubernetesPodOperator in an afternoon if resume value ever matters. That is the concrete payoff of the modular design, so it is worth a sentence in the spec.

Dagster is the one to steal ideas from rather than adopt: name your Temporal workflows after assets, not jobs. MaterialiseAsset(name, window) reads better than RunPipeline and maps onto dbt selectors directly.

dbt and Go transforms: the boundary and the build order

The spec's rule of thumb is right: if it can be a SELECT without pain it is dbt, otherwise Go. Two things make that rule operational rather than aspirational.

A transform contract both sides satisfy

Every transform, dbt or Go, declares the same four things: input table names, one output table name, a partition window, and its tests. A dbt model gets this from its ref() calls and schema.yml. A Go transform gets it from a small struct the orchestrator can inspect. The orchestrator then holds a coarse DAG of nodes tagged dbt or go, and dbt's own fine-grained DAG lives inside each dbt node.

Two dbt passes, not one

If a Go transform reads a mart and writes a table that another mart consumes, a single dbt build cannot express that. Tag models and run dbt twice around the Go step:

dbt build --select tag:pre_go      # staging + marts the Go step reads
go run ./cmd/transform drift --window 2026-09-14
dbt build --select tag:post_go     # marts that consume derived/drift

Or use selectors on the Go transform's declared output: dbt build --select source:derived.drift+ rebuilds exactly what depends on it. Either way, freshness tests on the derived source catch a Go transform that silently stopped, the same way they catch a dead extractor.

An alternative worth knowing about, not adopting. Bruin is a pipeline tool written in Go that does ingestion, SQL transforms, Python transforms and quality checks in one CLI with DuckDB support. It would collapse Fetcher, Writer, dbt and orchestrator into one tool. It would also mean not learning dbt, which is the industry-standard half of your stated goal. File it as a comparison point for a future post.

Warehouse path: what "industry standard" should mean here

The spec picks Redshift because it is approved in org, which is a perfectly good reason. Be honest in the spec about the other reason: for a solo project on this data volume, DuckDB never needs replacing. You move to learn the operational shape of a server warehouse, not because DuckDB ran out.

Two implications for the spec. First, Glue Data Catalog is a phase-2 dependency for both Redshift Spectrum and Athena, so it deserves a line in the phase table. Second, Iceberg is the thing that makes the warehouse genuinely swappable, because every engine above reads it and dbt-athena writes it. The spec is right to keep it out of phase 1, but "Later" undersells it: it is the phase-2 table format decision, not an afterthought. iceberg-go being read-heavy is fine, since the Go side only ever writes bronze Parquet under the external-table model above.

Dialect discipline. Keep staging models free of DuckDB-only syntax (read_parquet belongs in sources.yml, not in models; avoid list and struct types and QUALIFY) so that repointing dbt at Redshift is a profile change and not a rewrite. A tiny CI job that runs dbt compile against both targets would prove it.

A build order that teaches one thing per step

Ordered so each step is testable on its own and each introduces exactly one new data-engineering concept. The first four are a weekend; the whole list is a couple of months at an evening pace.

  1. Writer with deterministic paths, test-driven
    learn Idempotency. Path derivation from a window is pure Go and the perfect TDD target; assert that two runs of the same window produce identical bytes.
  2. One Fetcher for one concrete source, Runner as a loop
    learn Window versus cadence versus lookback. Pick a source that serves history so re-extraction is real.
  3. dbt-duckdb project: external source, one staging view, one mart, tests
    learn Medallion layering, external tables, dbt build semantics, source freshness. Run dbt docs generate and look at the lineage graph.
  4. Backfill command and a deliberately broken re-run
    learn Replayability. Delete a mart, rebuild from bronze, prove nothing was lost. Then corrupt a window and re-extract it.
  5. Wrap Fetcher and Writer as Temporal Activities under an IngestWindow workflow, drive with a Schedule
    learn Durable execution, activity retries and heartbeats, workflow determinism rules. Kill the worker mid-run and watch it resume.
  6. First Go transform writing to derived/, declared as a dbt source, two-pass build
    learn The dbt/Go contract. Something SQL genuinely hates: free-text parsing or a per-row model call.
  7. Second source, schema drift, union_by_name, compaction job
    learn Schema evolution and the small-files problem. Both will bite in phase 2 if not met here.
  8. OTel from the orchestrator and dbt run_results into Grafana
    learn Pipeline observability. Reuses existing workspace plumbing.
  9. Bronze to S3, dbt profile for Athena or Redshift Spectrum, Glue catalog, compile against both targets
    learn Storage/compute separation for real, dialect discipline, external catalogs.
  10. Temporal on EKS via Helm, workers as Deployments, Metabase against the server warehouse
    learn Disposable pods. Everything durable is in S3 and the warehouse, so delete the namespace and rebuild it.

Decisions only you can make

  • Which source goes first? A plant sensor once you have one, or beads history now. Both are real data you use. Beads has cleaner history semantics.
  • Redshift or Athena for phase 2? Redshift for org relevance and the classic warehouse operational experience. Athena for the cheaper, more Parquet-native path and Iceberg from day one. The spec can keep Redshift as primary and name Athena as the fallback, or swap them.
  • Does Airflow familiarity matter for you professionally? If yes, plan a one-week spike in phase 2 wrapping the Go binaries. If no, drop it from the spec entirely.
  • Metabase in phase 1 at all? Given the DuckDB lock constraint, DuckDB's built-in UI does the validation job with zero setup.

When you have picked, the spec edits are small: the raw-layer wording, the window/cadence/lookback definitions, principle 5, the Go transform zone, and the phase table gaining a Glue row and a Temporal-dev-server row.
